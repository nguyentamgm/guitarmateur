# Adding a language to Guitarmateur

Guitarmateur's UI text lives in one JSON file per language. You do **not** need to know
TypeScript, React, or how the app works internally to add a new language — you need a text
editor, a translation, and a pull request. This guide walks through the whole thing.

If you get stuck, [open an issue](https://github.com/nguyentamgm/guitarmateur/issues) and ask —
that's what it's there for.

## The five-step recipe

1. **Fork the repository** on GitHub (button in the top right of the repo page), then clone your
   fork to your computer.

2. **Copy the English catalog** to a new file named after your language's
   [BCP-47 language tag](https://en.wikipedia.org/wiki/IETF_language_tag) (usually just the
   two-letter ISO code — `fr` for French, `de` for German, `pl` for Polish):

   ```bash
   cp src/i18n/locales/en.json src/i18n/locales/fr.json
   ```

3. **Translate the values.** Open `src/i18n/locales/fr.json` in any text editor. It's a flat list
   of `"key": "value"` pairs, sorted alphabetically. **Leave every key (the left side) exactly as
   it is.** Only translate the value (the right side, in quotes). For example:

   ```jsonc
   // before
   "common.share": "Share",
   // after (French)
   "common.share": "Partager",
   ```

   Read [Key namespaces](#key-namespaces), [What NOT to translate](#what-not-to-translate), and
   [Placeholders and plurals](#placeholders-and-plurals) below before you start — they explain a
   few keys that need special care.

4. **Register your language in two files.** These are the only code-like changes required, and
   both are copy-paste edits — no logic to write.

   In `src/i18n/types.ts`, add your tag to the `LocaleId` union:

   ```ts
   // before
   export type LocaleId = 'en' | 'vi';
   // after (adding French)
   export type LocaleId = 'en' | 'vi' | 'fr';
   ```

   In `src/i18n/locales/index.ts`, import your JSON file and add it to both `MESSAGES` and
   `LOCALES`:

   ```ts
   // add this import near the top, alongside the existing ones
   import fr from './fr.json';

   // add 'fr' to MESSAGES
   export const MESSAGES: Readonly<Record<LocaleId, Partial<Messages>>> = { en, vi, fr };

   // add a LOCALES row — endonym is your language's name for itself, e.g. 'Français', not 'French'
   export const LOCALES: Readonly<Record<LocaleId, LocaleMeta>> = {
     en: { id: 'en', endonym: 'English', tag: 'en' },
     vi: { id: 'vi', endonym: 'Tiếng Việt', tag: 'vi' },
     fr: { id: 'fr', endonym: 'Français', tag: 'fr' },
   };
   ```

   The `tag` field is used to pick the right pluralization rules for your language (see
   [Placeholders and plurals](#placeholders-and-plurals)) and to set the page's `<html lang>`
   attribute — use the plain language subtag (`fr`, `pl`, `de`) unless your language genuinely
   needs a region (e.g. `pt-BR` vs `pt-PT`).

5. **Check your work** (see [How to check your work](#how-to-check-your-work) below), then commit
   your two new/changed files plus the two edited files, push to your fork, and
   [open a pull request](https://github.com/nguyentamgm/guitarmateur/pulls). Mention in the PR
   description that this is a new locale and how you verified it (native speaker, machine
   translation reviewed by a native speaker, etc.) — reviewers can't judge translation quality
   themselves, so that context matters.

That's it — five steps, two files translated/created, two files edited by copy-paste.

## Key namespaces

Every key is `namespace.name`, and the namespace tells you where the text shows up:

| Namespace | Covers |
|---|---|
| `app.*` | App title, subtitle, and header copy |
| `common.*` | Shared controls: share, export, import, language, left-handed toggle |
| `scalebox.*` | Step 1 — key/scale/tuning pickers, position boxes, the fretboard diagram title |
| `progression.*` | Step 2 — chord progression builder, suggestions, the advanced chord adder |
| `practice.*` | Step 3 — practice licks, difficulty levels, target-note controls |
| `playback.*` | Transport controls — play/stop, tempo, count-in, swing, loop, volume sliders |
| `legend.*` | Fretboard diagram legend (root, chord tone, scale note, blue note, target) |
| `error.*` | The error screen shown if the app crashes |
| `install.*` | The "install as an app" (PWA) prompt |
| `tab.*` | Guitar tab display (currently just the empty-lick label) |
| `scale.*` | Scale display names (Minor Pentatonic, Dorian, …) |
| `quality.*` | Chord quality display names (major, minor, dom7, …) |
| `tuning.*` | Tuning display names (Standard, Drop D) |
| `role.*` | Chord-tone role labels (Root, 3rd, 5th, 7th) |
| `note.*` | Note letter names (`note.letter.A`–`note.letter.G`) |

You can see every key with its current English value in `src/i18n/locales/en.json`.

## What NOT to translate

Some values in `en.json` are musical notation, not prose. Translating them would make the app
give musicians wrong information, so leave these exactly as they are in English:

- **Note letter names**, `note.letter.A` through `note.letter.G` — these are the seven letters
  used in standard music notation everywhere (`A`, `B`, `C`, `D`, `E`, `F`, `G`), not English
  words. Almost every language that uses guitar tab uses these same letters.
- **Chord quality suffixes** — `quality.M7` (`maj7`), `quality.m7` (`min7`), `quality.dom7`
  (`dom7`), etc. These are notation abbreviations musicians read internationally, like `♭` or `#`.
- **Roman numerals** used for harmony (e.g. `iv`, `♭VII`) — these don't appear as translatable
  catalog keys, but if you see them while testing, they are notation, not text.
- **Interval labels** (e.g. `♭3`, `♭5`) — also not translatable keys, but generated notation.
- **Guitar tab digits and fret numbers** — always plain `0123456789`, never localized digits.
- **Transport glyphs** — `▶` `■` `↻` `×` `·` `—` (play, stop, regenerate, remove, separator,
  dash). These appear inside a couple of string values (e.g. `practice.regenerate`: `"↻
  Regenerate"`) — keep the glyph, translate the word next to it.
- **The product name "Guitarmateur"** — never translated or transliterated. It appears inside
  `install.title` (`"Install Guitarmateur"`) — translate "Install", keep "Guitarmateur".
- **"REC"** (`scalebox.recommended`) and **"BPM"** (`playback.bpm`) — both are short technical
  abbreviations used by musicians internationally (recommended position, beats per minute). Keep
  them as-is unless your language has an equally-short, equally-standard abbreviation in common
  use among musicians — if unsure, keep the English abbreviation.

## Placeholders and plurals

### Placeholders

Some values contain `{name}` placeholders that get filled in with real data at runtime — a chord
name, a number, a note. **Keep every placeholder token exactly as spelled** (same `{curly
braces}`, same name inside), because the code looks them up by that exact name. You *may* move a
placeholder to wherever it belongs in your language's word order — that's the entire reason
placeholders exist instead of concatenated strings.

For example, English builds the scale-box title as `{tonic} {scale}` — tonic first:

```jsonc
"scalebox.title": "{tonic} {scale}",   // "A Minor Pentatonic"
```

Vietnamese reverses the word order — the scale name comes before the key in natural Vietnamese
phrasing — which is fine, because both placeholders are still there, just reordered:

```jsonc
"scalebox.title": "{scale} chủ âm {tonic}",   // scale name, then "chủ âm" (tonic), then the key
```

The rule the automated check enforces is: **the same set of placeholder names, in any order** —
not the same order, not the same count of each (a placeholder may even repeat if your grammar
needs it). If `en.json` has `{count} bar` and your translation drops `{count}` or renames it to
`{n}`, the check will fail and tell you exactly which key is wrong (see
[How to check your work](#how-to-check-your-work)).

### Plurals

A few English values change shape depending on a count — "1 bar" vs "2 bars". These are stored as
**two separate keys** sharing a base name, one per grammatical "plural category":

```jsonc
"progression.bars.one": "{count} bar",
"progression.bars.other": "{count} bars",
```

At runtime the app calls `Intl.PluralRules` (a built-in browser API) with your language's tag to
decide which category — `one`, `other`, and in some languages also `zero`, `two`, `few`, or
`many` — applies to a given number, then looks up `<base>.<category>`.

**Different languages need different sets of categories.** English needs only `one` and `other`.
Vietnamese has no plural inflection at all, so `vi.json` supplies only `progression.bars.other`
and uses it for every count. Polish is a good example of a language that needs more: Polish plural
rules distinguish `one` (1), `few` (2–4), `many` (5+ and most other cases), and `other` (fractions),
so a Polish translation would need all four:

```jsonc
"progression.bars.one": "{count} takt",
"progression.bars.few": "{count} takty",
"progression.bars.many": "{count} taktów",
"progression.bars.other": "{count} taktu",
```

You don't need to guess which categories your language needs — the automated check
(`src/i18n/locales.test.ts`) asks `Intl.PluralRules` for your exact tag and tells you which
`<base>.<category>` keys are missing. Add exactly the ones it lists, using whatever plural forms
are correct for your language.

As of this writing, `progression.bars` is the only plural key in the catalog.

## How to check your work

You don't need to understand the app's code to verify your translation — one command checks
everything:

```bash
npm ci
npm test
```

(`npm ci` installs dependencies from scratch the first time; `npm test` runs the automated test
suite, which includes `src/i18n/locales.test.ts` — the test that validates every locale file.)

If your translation is complete and well-formed, the tests pass and you're done. If something's
off, the failure message tells you precisely what to fix. Here's what that looks like — this is a
real failure produced by a locale file that was missing a plural form, had a typo'd placeholder,
and had one leftover made-up key:

```
FAIL  src/i18n/locales.test.ts > locale catalogs > every shipped locale is a clean translation of en
AssertionError: vi: missing=progression.bars.other unknown=made.up.key
placeholder=scalebox.title pluralForms=progression.bars.other: expected { …(4) } to deeply equal { missing: [], unknown: [], …(2) }

- Expected
+ Received

  {
-   "missing": [],
-   "missingPluralForms": [],
-   "placeholderMismatch": [],
-   "unknown": [],
+   "missing": [
+     "progression.bars.other",
+   ],
+   "missingPluralForms": [
+     "progression.bars.other",
+   ],
+   "placeholderMismatch": [
+     {
+       "actual": ["scale", "tonik"],
+       "expected": ["scale", "tonic"],
+       "key": "scalebox.title",
+     },
+   ],
+   "unknown": [
+     "made.up.key",
+   ],
  }
```

Reading it:

- **`missing`** — a key that exists in `en.json` but not in your file. Copy the key from
  `en.json` and translate it. Here, `progression.bars.other` was accidentally deleted.
- **`unknown`** — a key in your file that doesn't exist in `en.json` at all — usually a typo in
  the key name, or a leftover you added by accident. Here, `made.up.key` should be removed.
- **`placeholderMismatch`** — a key exists on both sides but the `{placeholder}` names don't
  match. `expected` is what `en.json` uses; `actual` is what your file has. Here,
  `scalebox.title` had `{tonic}` accidentally retyped as `{tonik}` — fix the placeholder name
  (you can still reorder it, just spell it exactly like `en.json`).
- **`missingPluralForms`** — your language's plural rules need a `<base>.<category>` key you
  haven't supplied yet. Add it with the correct translation for that category.

Fix each item the message names, re-run `npm test`, and repeat until it's green. You can also run
`npm run typecheck` and `npm run lint`, but for a translation-only PR they should already pass
without you touching them — `npm test` is the one that actually validates your JSON.

## Current limitations

Please read this before starting, so there are no surprises in review:

- **No right-to-left (RTL) support.** Guitarmateur currently only supports left-to-right
  languages. Adding a language like Arabic or Hebrew would require a separate layout effort
  (mirroring the UI, `dir="rtl"`, and CSS changes) beyond translating text — it's not something a
  translation-only PR can add.
- **`index.html` and `public/manifest.json` are not localized.** The page `<title>`, meta
  description, and PWA manifest name/description stay in English for every visitor, regardless of
  their chosen in-app language. Only the in-app UI (and `document.title` once the app has loaded)
  reflects your language.
- **Digits are never localized.** Every number in the app — BPM, fret numbers, practice level,
  bar counts — is guitar/music notation or a control value, not prose, so it's always shown with
  plain Latin digits (`0123456789`), even in languages that traditionally use other numerals.
  Don't localize digits in your translated strings.

## Credit

You can add your name (or handle, or however you'd like to be credited) to your locale's entry in
`src/i18n/locales/index.ts` via the optional `contributors` field:

```ts
fr: { id: 'fr', endonym: 'Français', tag: 'fr', contributors: ['Your Name'] },
```

It's a free-form list of strings, so multiple people can be credited on the same locale — just add
more entries to the array. This field is purely informational credit; it doesn't affect anything
functionally.
